# 可达汇报约定：需求与审查

状态：本地候选，待本地review；不表示远端发布、端侧读取或真实业务采用。唯一规范正文见[可达汇报约定](../../skill/organization-collaboration/references/context-and-reporting.md#派发时约定可达汇报)，其他规则复用既有规划、记录与交接。

## 需求与辩证结论

用户指出执行端联系不到指定接收者，并要求“这个在派任务的时候要说清楚”“辩证优化，固化为一条协作规范”。背景为独立诊断已形成报告，但派发未说明可达的交付通道，控制端读取与转交延迟。公开稿只保留此抽象情境，实际对象、会话和路径在原受控任务中维护。

目标不是强制执行端拥有直连能力，而是让派发者同时落实交付和读取责任。推送适合已有有效通道；拉取适合单向或隔离执行器，不必为汇报新建服务或扩权。仅说“报告已放好”会把发现责任悬空；反过来要求每次都等最终接收者回复，会拖住无依赖工作。最小平衡是约定可达落点、拉取责任与有界检查，分开记录事实；依赖决定和写权的步骤仍不可抢跑。

兼容性：这是对既有 `report_route`、下一责任人／检查点及证据分层的说明补丁，组织协议候选1.5.2、组合源码候选0.9.3；不增加必填全表、岗位或运行权限。新任务引用该条，在途仅于明确检查／交接点补缺项，保留原引用和有效授权，不重开执行。未声称已有自动路由、唤醒或定时监控。

## 小范围验收与反例

以下为本地文档走查，不以它代替真实端侧行为试验。审查者按输入核对主规则能否给出右栏行为；真实采用时另取准确任务、版本与受控证据。

| 输入／反例 | 必须满足的判据 |
| --- | --- |
| R01：执行端只能在原任务留报告，不能向负责人推送；派发者有读取入口 | 派发时指定落点和已获准拉取者、检查点／最迟复查点；派发者确认承接并落实读取或中转，不能仅要求“自行联系负责人” |
| R02：报告链接存在，工具返回ACK，中转者已读，但负责人尚无读取证据 | 分列保存、发送、受理、中转者读取；最终接收者读取、采用与写权交还仍未确认；不能以链接或ACK代替 |
| R03：报告完成，另有已授权独立整理；共享资产仍由别的执行者写入 | 独立整理继续；无其他就绪项可交接并结束本轮，不空等；共享资产不得因报告完成或超时而抢写 |
| R04：检查点未取到报告，重复探测没有新信息；有未知派发请求 | 依预算停止该轮探测并保留待办、下一责任人和触发；不无限轮询，不重派UNKNOWN；未完成不能记成功 |
| R05：内部报告可保存，但指定接收端访问未验证；建议改发公开链接或复制凭据 | 只保存获准结果并说明待交付；核必要通道缺口，不擅自公开、换收件人或传递凭据；纯查询不冒充消息送达 |

审查范围：核心规则一处、入口短导航、分流措辞消歧、当前候选版本及需求索引。仓库结构与单元测试只证明离线资料／工具回归；不证明真实消息已读、业务采用、写权交还或额度／延迟改善。
