# 局部阻塞与并行交付迭代

2026-10-28，设计版本1.0。公子已授权整理并实现本轮通用规范，目标是缩短独立工作等待和交付验收周期，避免一个排查问题阻塞整个项目。授权覆盖仓库规范、模板及验证；项目阈值试行、实际派发和生产另按已有项目授权与采用记录执行。本页是本次迭代设计，运行规则唯一正文仍为[规划与进度](../../skill/organization-collaboration/references/planning-and-progress.md)，执行状态沿[原任务队列](../../.codex/agent-state/todo.md#当前环境与下一步)。

## 输入与取舍

输入为公子转交的《凡人二创项目并行任务治理方案》v1，以及随后确认的通用方案和“效率优先、一个排查问题不阻塞整个项目”要求。原提案的4个执行槽、6个在制任务、待验2个、GPU单作业及观察窗口均为项目建议，不是已经生效的全局规则。具体项目背景不作为本轮实时状态，不复制材料路径、私密会话或业务明细。

| 原提案的价值 | 推广时的张力 | 本轮决定 |
| --- | --- | --- |
| 阻塞不能使任务从承诺中消失 | 单项故障或全量刷新容易变成全项目等待 | 明确受影响依赖／资源；独立就绪工作继续，只补当前决定所需证据 |
| 区分执行与在制积压 | 会话、人员、后台作业和交付物不是同一计数单位 | E按实际独立活动及未解除预留，W按独立承诺成果，Q按待验成果去重；范围和单位显式记录 |
| 限制待验库存 | 一个验收队列拥堵可能错误冻结其他能力 | 按实际共用验收能力限制增量生产；复核、必要返工和解阻保留可执行路径 |
| 取消前处理残留 | 强制等待执行终态才承认业务取消，会拖住全部承诺 | 有效业务退出和必要承接与运行状态分列；W解除不自动释放E或冲突资源 |
| 统一派发避免抢槽 | 两个项目各自唯一派发者仍可能争抢同一资源 | 只对发生争用的容量范围明确当前准入协调者，串行核验／预留／派发／回执；不锁全组织记录 |
| 用指标调整容量 | 把4/6/2或七天当组织硬标准会新增停工门槛 | 参数、观察窗口和复盘依据归项目配置；不凭少量样本宣称效率提升 |

## 责任与实施边界

架构路径：`BOUNDARY_NOTE`。在原有组织规划和追溯合同中增加可选的阻塞、容量及资源预留信息；项目负责人仍决定目标、派工与最终验收，总负责人仍协调跨项目优先级和资源，原派发者仍负责未知请求对账，记录者仍只核据登记。平台原生执行、GitHub当前记录及验收回执各自保留权威来源。准入协调属于已有资源职责的范围内委派，不新增组织岗位或技术锁服务。

- 通用规则、最小模板和岗位导航归组织协作skill。
- Projects、Lody和Cloud的具体查询／派发／恢复沿现有操作入口，不另写调度API。
- 项目配置只记录采用范围、阈值、资源与验收能力、协调者、依据和复核条件；例子不自动生效。
- 不新增数据库、常驻轮询、全组织写锁或自动派发器；普通工具调用、小步骤和无竞争的小任务不套完整容量流程。

## 可实施的最小闭环

1. 从当前正式记录取得任务、输入版本、授权和验收依据。只刷新本次判断依赖的范围；恢复时未读完的范围明示，不阻断已取得充分依据的独立任务。
2. 遇到问题先确定受影响任务／资源，同时列出可继续项。排障有本轮目标、允许副作用、预算、停止／交接点和下一触发，不能用“正在排查”无限占住整个项目。
3. 对候选按独立交付与依赖拆分；已有任务继续沿原关联。能减少关键路径等待且输入、工具、资源、验收均满足的工作优先；空槽不产生新业务授权。
4. 若已采用容量限制，按各自适用范围核E/W/Q和资源。既有成果内的返工／复核不重复增加W，独立新承诺另计；验收受阻时限制会增加该瓶颈库存的生产。
5. 在同一共享名额存在竞争时，当前准入协调者确认预留，再由任务指定派发者执行一次并回填。授权工具不提供原子事务时，只承诺协作约束和对账，不声称技术上恰好一次。
6. 按原任务报告进展、停止、阻塞、产物和验收。已取消但执行未知的残留继续承接；恢复或新尝试须重核容量、输入及旧尝试状态，不重建同义任务。

此闭环适用于软件、研究、文档、设计和媒体交付。原件默认在所在端复核，传输附件或用户试听只在具体任务明确要求时发生。制作自检、独立质量复核与负责人验收不合并。

## 项目配置与最小记录

通用技能提供可引用的字段，不要求增加全部Project字段或新建配置服务；沿原任务正文和事件保存，摘要由任务记录汇总。具体模板以[规划与进度](../../skill/organization-collaboration/references/planning-and-progress.md)为准。

| 记录位置 | 最小信息 |
| --- | --- |
| 项目／共享资源采用记录 | 适用范围与单位、已采用限制、当前准入协调者、资源／验收能力、有效依据及复核条件；未设定不填造默认值 |
| 阻塞与排障回执 | 阻塞对象、受影响任务、可继续项、本轮排障目标与预算、下一责任人和解除／交接条件 |
| 任务与执行关联 | 独立成果及是否计入W、真实执行单元／预留及资源、执行轮次、观察时间与证据；未知执行和记录待补写分列 |
| 项目摘要 | 当前范围内E/W/Q、实际瓶颈、下一项安排、未覆盖范围；不维护另一套手工事实源 |

凡人二创可以评估采用E=4、W=6、Q=2，但本迭代不替该项目负责人启用它们。GPU按实际设备或共享池约束，不把所有项目的GPU串成一个槽；最终验收窗口属于真实验收人，不由Agent槽位替代。W满而确需独立解阻任务时，由负责人按既有权限明确调整承诺或容量，或者使用已约定的恢复容量，不能默默超限，也不能永远挡住唯一解阻路径。

## 验收与效果证据

核心验收：A正在排查时，B的授权、输入、资源和验收条件独立满足，B能够继续；A的未知执行与冲突资源仍保留。其他场景覆盖同输入阻塞的正确传播、排障预算、子执行计数、W满恢复、取消残留、记录同步未知、验收瓶颈范围、解阻容量、跨项目抢槽、部分覆盖、空槽候选、成果与复核去重、参数未采用、在途撤权及延期老化。输入和逐项判据统一保存于[行为输入](eval-inputs.json)与[评分规则](eval-rubric.md)，不写固定措辞匹配测试冒充行为验证。

仓库按既有命令运行结构和Python测试；知识行为另由独立前向走查验证。真实采用后才观察独立工作等待、最终验收数、承诺到验收周期、阻塞范围、返工及待验积压，以及重复派发／冲突写入。尚无实测对照，不宣称吞吐、延迟或成本改善。是否调整参数由对应负责人依据实际样本决定，不以填满槽位为目标。

## 采用与在途处理

本轮交付通用规范和分发产物；每个实际项目在原正式入口确认采用版本、适用范围及必要容量配置。未采用的项目保留原规则；在途任务按明确节点补充受影响信息，不重开、不重新派发、不抹掉旧证据。撤权、公子新指令和当前安全约束立即生效，不受旧版冻结保护。

新组织协议只要求变化所涉及的岗位读取对应正文和规划参考。旧1.3.0与组合0.7.0／0.7.1的回执保留原范围；新1.4.0／0.8.0的文件接入、实际读取、原生发现与真实项目采用各自记录。未变的Projects操作方法与专业内容无需重跑整套验收。正式看板／人员绑定不由这次仓库更新自动改变。
