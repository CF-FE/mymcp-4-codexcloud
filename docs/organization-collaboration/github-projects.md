## 2026-10-28：看板统一入口与追溯增量

公子确认各角色优先以正式看板记录理解全局。接单、跟进、交接和下一步判断先查准确条目及关联任务／有效回执；无直接读取条件时使用授权记录者的标源回执。看板是入口，原生运行和验收仍由其证据来源解释；冲突或滞后标待核对，由当前写者核证补写，不凭聊天摘要覆盖，也不拿旧字段消除真实执行。

代码交付时已收到一个项目的私有看板创建回执，并只读核对其元数据；当时没有核任务条目、历史补录或负责人接入。准确项目绑定、专职负责人会话与执行位置保留在受控项目记录和私密交接，不提交到通用技能。后续已获准公开的登记摘要及限定切换见下节；组织共享职责与项目职责分别绑定，机器名称不代替任职。

看板首屏提供任务关联、负责人、当前阶段、阻塞、下一责任人与动作，以及执行／产物／验收／审计摘要入口；优先复用已有字段与Issue链接，不预设每项都创建自定义字段。项目关键决定保留在项目正式记录并关联受影响任务；普通事实与更正追加原任务事件。通用模板见[追溯指引](../../skill/organization-collaboration/references/task-traceability.md)，审计核对见[流程审计者](../../skill/organization-collaboration/references/auditor.md)。

审计报告只记录其实际窗口、来源和覆盖。看板列表要与获准的需求及原生派发／执行记录对照，含已关闭、取消、迁出和未决派发；没有完整外部来源就不能宣称无漏登。审计发现由项目负责人组织整改，审计者复核，状态登记仍沿当前写者，不把审计变成所有任务的额外审批。

切换前绑定记录路由、当前写者、负责人和可用通道；如本次已安排审计，再绑定其获准范围与接收者。核旧任务与执行引用映射；记录采用版本及切换点。历史补录分开发生、观察和登记时间，不追认未知授权。未切换任务沿原正式入口；已运行任务补关联，不重派。后续回退入口也要交接新事件和未知写入，不能把旧快照恢复为当前事实。

## 较早的委托访问方案

以下为1.2.1发布时的接入事实及可选委托路线；当前直接读取方向以上节为准。

公子已明确：云端Dot当前没有GitHub Projects直接授权，查询和登记通过授权记录者完成。**Dot发请求 → 记录者用获准连接查询／核对／写入及回读 → 沿原通道回传 → Dot核对并作其职责内的判断。** 本机独立MCP读写已有历史证据；mac-work内承担记录职责的具体Lody会话、工具入口及请求回传闭环尚未验通，不能按机器名称继承本机终端的结果。

Dot自身的Projects直接读写在当前分工下为“不适用”，不列成待补授权，也不要求安装GitHub MCP或复制本机凭证。Dot只需具备读取组织协议、提出清楚请求、核对记录者回执及沿原任务继续协作的能力；实际GitHub访问证据归执行查询／登记的记录端。

这是当前接入事实，不是永久禁止Dot使用任何GitHub连接。后续若采用Lody等获准连接，按实际操作者、工具、目标权限和回执更新接入记录；由谁承担记录职责仍须明确。已有参与者可以兼任，不为岗位名称强制再创建会话；同一参与者兼任也须保留决定来源、冲突核对和写后回读。

查询请求明确对象或范围、所需字段及用途；回执带相同请求关联、实际对象、观察时间、筛选／状态范围、分页覆盖、结果及未取得项。记录者按任务授权回传必要内容，Dot注明“经记录者取得”；GitHub访问权与组织中获准接收报告分别判断。查询失败、权限拒绝、部分分页或过时快照不能当作不存在或当前成功状态。已有获准中转通道可以使用，不以自动直连为唯一有效通道，但中转来源及送达范围须如实记录。

必要状态缺失或冲突时，Dot请求原记录者定向核对，暂停依赖它的派发／关闭等动作；记录者不可达不自动触发给Dot扩权、转发令牌或新建相同任务。原生执行状态仍由原执行／派发责任人提供，GitHub看板回执不能证明Cloud已停止或产物已验收。

| 信息 | 正式来源 |
| --- | --- |
| 任务身份、目标、范围、交付与验收条件 | Issue 正文；重大变更保留决定依据 |
| 成员组成和分工 | 父任务的职责说明及子 Issue，引用已有任职关系；不另抄完整组织名单 |
| 当前工作阶段、优先级、下一责任方、目标日期 | 选定 Project 的字段；日期仅在有承诺时填写 |
| 父子分解、子任务进度 | 原生父子 Issue；“属于哪个成果”与“被什么前置阻塞”分别记录 |
| 依赖及放行 | Issue 依赖关系＋约定输入版本和放行条件；日期到了或子项关闭不自动触发执行 |
| 进展和证据事件 | Issue 评论或已有受控证据记录的可公开摘要／引用 |
| 实际执行状态与过程 | 原 Cloud／Lody 任务和回合，保留原生 UNKNOWN 等状态 |
| 最终验收 | 负责人绑定精确产物的[回执](../../skill/organization-collaboration/references/context-and-reporting.md#产物复核与验收回执)，记录者引用其决定 |

GitHub Assignees 填实际合适的 GitHub 账号；AI 名称、组织岗位和专业角色写在职责说明中，不假装它们是可分配账号。字段名称和 ID 以目标看板实际返回为准，不能把示例 ID 写入技能。

初始看板可用七个阶段：待审阅、待开始、执行中、阻塞、待复核、待验收、已结束。阻塞项写清解除条件及下一责任方；“已结束”同时注明完成验收、取消、重复或不再执行的原因。检查项仍使用通过／不通过／未验，不能把阶段当检查结论。GitHub 原生关闭原因能表达时同步使用，无法直接表达的业务原因留在 Issue 决定记录中。

这些阶段和字段是待正式看板采用的最小模板，尚未在远端创建。先沿一个真实任务验证，再按需要调整；不先引入工时填报、复杂百分比、自动派发器或双向状态同步。

## Codex Cloud 派发前关联

正式切换到GitHub的项目，新独立Cloud委派按以下顺序执行：

1. 负责人审阅任务；Dot自身的协调任务由Dot在其权限内审阅。
2. 授权记录者查相关在办、未决创建及父子关系，创建或关联原Issue，核对正式Project中的条目；准确引用和当前阶段须已回读。
3. Dot直接读取或核记录者标源回传的准确Issue／Project关联和覆盖、观察时间，并结合原执行端的已有运行／UNKNOWN及依赖条件，携带任务引用、范围、输入版本、验收和汇报通道创建一次Cloud任务；此核对不要求Dot直接查询GitHub。
4. 将实际Cloud任务／回合关联保存到同一业务任务的受控记录；公开Issue仅回填可公开摘要或引用，私有Issue也核当前访问授权。后续产物、质量复核、负责人验收和关闭继续沿该任务对账。

一个Issue可关联多次有明确理由的执行或续跑，不按每次工具调用或实现步骤拆Issue；独立子成果才新建子任务。Dot自身协调工作也有组织任务记录，使用默认仓库，不假造项目负责人。派发前的登记是管理流程，由现有工具执行；仅安装MCP不会自动产生这一关联，本仓库没有部署自动派发器。

记录者回执证明记录系统中的关联和状态，已有Cloud是否运行、创建是否UNKNOWN仍由Dot／原派发责任人按原生引用核实；Project显示“待开始”不能单独证明没有既有Cloud执行。

切换后，必要Issue／Project关联缺失或创建结果UNKNOWN时，暂停依赖它的新独立派发；临时例外须有明确授权并保留待补登记的原任务关联，不能默默绕过。已经运行的任务继续按原授权处理；Cloud创建成功而GitHub回填失败时保留原生引用，先对账和补登记，不能重建Cloud。切换前沿项目原有正式入口，既有运行补关联但不为迁移重跑。各项目须分别确认切换；看板创建回执不足以宣称这一GitHub闭环已全局启用。

## 授权记录者的分工

授权记录者是 `executor` 的可委派职责，不为记录职责另增岗位或专业库角色。某位负责人有工具和授权时可自行记录；也可委派本机等合适执行端。每个条目的当前写入者和范围明确，不同条目可由不同记录者处理。

代录请求复用原任务，最少包括：**目标 Issue／Project 条目、需要更新的内容、决定者及依据、证据引用、回报对象**。受理、实际进展和检查证据可按预先授权更新；范围、派工、验收和关闭依据不能由记录者自行编造。项目仍要求负责人独写的正式入口，须继续遵守，不能由通用代录条款绕开。

记录前按[授权记录者职责](../../skill/organization-collaboration/references/authorized-recording.md)定向核对：创建时查相关在办和未决请求；更新时防旧版本或迟到报告覆盖新状态；关闭时区分完成验收与取消／重复决定，并核在途执行和后续承接。相似标题不自动合并，建单不等于批准执行。缺依据或冲突保留提报、当前值及下一责任人，暂停该项覆盖，不追加全项目审批。

写后回读并沿原获准通道报告。项目记录与 Issue 状态不是原子更新：已经成功的部分保留，未完成部分记待登记；结果未知先查原对象，不重复建单。具体记录入口不可用时，其他已授权无依赖工作继续；更换记录者或连接须交接当前写者、未决请求及回报路径，不复制个人令牌或另建权威队列。

## 可见性与权限

默认环境仓库当前为 public。公开 Issue 只写可公开的目标、进展及证据摘要；内部路径、真实会话、完整任职关系和素材保留在项目受控记录，链接本身也须可公开。连任务存在性都不能公开时，先指定合适的私有任务仓库。私有 Project 和筛选视图不会使公开 Issue 变为私密。

实际访问分别取决于账号对目标的权限、凭证范围和执行端连接；岗位任命与任务授权另核。`project` OAuth 范围并不只限 CF-FE，CF-FE 是本次批准的操作范围，不能冒称技术上已经组织隔离。凭证撤销或过期后须重新核访问，不把“固化”解释为永久不可撤销。
