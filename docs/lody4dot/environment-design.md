# 环境架构设计参考

本页是[环境指引](environment-model.md)的技术附录，整理日期2026-10-21。面向需要设计跨会话、跨执行器协作的开发者。平台事实以所引官方来源为准；下述记录项和JSON是项目建模建议，不是平台现有API或已接受的实现方案。

官方已确认Dot是ChatGPT中的常驻Agent产品/服务；通用Agent角色与该产品名称并非互斥。建模时将Dot及其工作上下文，与Dot云电脑、它创建的Codex云任务环境和获授权本地电脑分别关联；不把Dot当任意Agent或单台机器的别名。多宿主协作的具体方案见[开发方案](collaboration-development.md)。

## 建模前先检验这些假设

现有指引将容易混淆的对象分别识别，这一方向成立；进一步设计时，还要处理以下反例。

| 看似方便的假设 | 实际张力或反例 | 采用的表述与取舍 |
| --- | --- | --- |
| 给Agent记一个“本地/云端”位置即可 | 同一Agent可以调用云shell、本地工具和远端MCP；模型服务还可能在别处。 | 每次操作关联工具连接及目标执行器。多记录一层，换来准确定位；模型服务位置另记或保留未知。 |
| Dot就是它使用的某台云电脑 | Dot有自己的云电脑，也能创建预配置的Codex云任务或授权本地任务；更换所选电脑不迁移既有任务。 | 产品/Agent身份与各任务执行器分别关联，不能用Dot产品名覆盖实际执行位置。 |
| 发布配置版本就是可恢复快照 | 配置激活与依赖文件恢复是不同事实；变量/网络更新也可能不同于源码或进程更新。 | 发布配置、安装产物及目标实例的应用结果分别关联，不预设平台快照实现。 |
| 每个产品都须重新授权同一个插件 | 官方明确既有插件连接和权限跨Dot、ChatGPT、Work、Codex共享；本地访问和浏览器登录另有边界。 | 优先复用实际可用的已授予连接；另核对执行器、本地授权、CLI状态和目标资源范围，不建立新的统一凭证池。 |
| 全部对象权限预先证明后，才能发起请求 | ACL常要通过已授权的只读请求才能确认。 | 在任务授权和可用工具范围内检查访问，根据服务端返回区分允许、拒绝和未知。 |
| 信息越全越容易理解 | 平台概念、当前测试结果和设计建议混排，会把临时状态读成通用规则。 | 主指引按使用问题组织，日期明确的现状单列，本页承载技术记录。 |

这保留了原有边界的价值，同时避免用统一的“环境”“会话”“权限”字段承载不同系统的事实。当前没有证据要求增加通用运行平台、统一凭证池或新的编排服务。

## 分别记录哪些对象和关系

| 记录 | 关键关联 | 回答的问题 |
| --- | --- | --- |
| Agent与工具连接 | Agent上下文、工具连接、目标执行器/业务系统 | 这次操作通过哪个入口、在哪里发生？ |
| 产品、执行器与安装能力 | 产品/Agent、具体执行器、OS/架构、加载入口、已观察的控制/执行能力 | Dot产品组织了哪些任务，插件实际装在哪个执行器、能承担什么角色？ |
| 会话与云任务 | 来源系统、对象类型、会话引用、任务引用和来源 | 消息上下文与平台工作单元如何对应？ |
| 任务与运行实例 | 任务、实例、绑定时间与观测来源 | 操作的是哪个实例？绑定是否改变？ |
| 配置与安装产物 | 发布配置、源码commit、插件/CLI版本、产物哈希及恢复证据 | 发布了什么，实例实际用了什么？ |
| 资源引用 | 系统、对象类型、标识与来源 | 目标是对话、文件、机器，还是业务会话？ |
| 授权与访问检查 | 用户授权范围、工具、目标对象、检查结果及原因 | 允许做什么，实际访问到了什么？ |
| 已有插件连接与独立状态 | 连接来源和授予范围、本地访问、浏览器登录、CLI状态、模型身份 | 哪些授权已按平台共享，哪些运行条件仍需本端单独满足？不记录凭证值。 |
| 操作与结果证据 | 控制端、执行端、session/turn、产物、时间和来源 | 哪项结果能支持哪项结论？ |

不要预设会话、任务、实例和主机一一对应；新绑定按时间保留，不能用“当前最新实例”覆盖历史操作发生的位置。同一Git仓库的不同checkout也分别记录路径和commit。

## 最小记录示例

### 本项目任务创建与协作的职责

用户已确认Dot具备独立Codex云任务创建权限。当前云任务不创建另一个Codex云任务；CLI有同名命令不构成本端可执行能力证据。此处是本项目执行边界，不将其扩写成所有宿主的CLI通用限制。

| 动作 | 负责端 | 应保存的结果 |
| --- | --- | --- |
| 创建独立Codex云任务 | Dot，使用其已具备的权限选择已发布环境和仓库 | 实际任务引用、环境关联及Dot发起关系 |
| 加载lody4dot并接入Lody | 新云任务，在自身执行环境核实入口、依赖和身份 | 实际版本、首次读取来源及Lody工具结果 |
| 经Lody派发/观察及交接 | 具备合法工具与任务授权的Dot、云端或本地控制端 | Lody原生session/turn、产物及核验回执 |
| 汇总结果与后续协调 | Dot接收回传；协作者只交接必要引用与成果 | 可追溯的任务与产物关系，不共享身份文件 |

OpenAI任务目录查询与Lody协作属于不同接口。前者的历史401不作为后者或插件安装前置，也不列为项目待修复阻塞。

### 记录格式

先按上表记事实即可，暂不要求实现存储或统一schema。需要结构化交接时，可从下面的示意格式开始：

```json
{
  "observed_at": null,
  "evidence_origin": null,
  "conversation_ref": null,
  "task_ref": null,
  "runtime_ref": null,
  "environment_version_ref": null,
  "repository_commit": null,
  "plugin_version": null,
  "cli_version": null,
  "artifact_hash": null,
  "entry_discovery_source": null,
  "resource_reads": [],
  "access_evidence": null,
  "result_evidence": null
}
```

填写规则：

- 每个 `*_ref` 按“来源系统、对象类型、标识”记录；未暴露或未观察的引用保留null，不用占位ID冒充平台对象。仅有一个无命名空间的 `session_id` 不足以交接。
- `evidence_origin`说明平台工具、Agent执行记录或用户截图等来源；`entry_discovery_source`分别记录平台start_skill、仓库导航、自主检索或用户提供路径。
- `resource_reads`只列实际读取资源及必要版本；`access_evidence`记授权范围和实际检查结果；`result_evidence`定位持久化结果、产物或回执，并说明能证明什么。
- 时间、工具作用域和版本来自实际观察。示例不是完整执行日志；缺少目标、操作或结果时，不能据此宣称工作流验收完成。
- 凭证值不进入记录；真实业务标识保留在私密关联记录，公开报告仅保留必要的脱敏结果。

## 权限与证据如何判读

**任务授权**回答用户允许做什么，**连接授予范围**限定可用资源和操作，**服务端访问检查**回答当前请求能访问什么，**运行约束**决定工具实际能否完成操作。分别记录，避免把“技术上可访问”当作任务授权，或把“未知”写成拒绝。

| 已有观察 | 支持的结论 | 还需什么才能扩大结论 |
| --- | --- | --- |
| 当前没有空间枚举工具 | 当前无法通过此入口搜索整个空间 | 可用对象工具与其实际返回；不据此推断用户的空间ACL。 |
| Dot可使用已连接的ChatGPT插件 | 已有连接可在其授予范围内共享使用 | 当次工具暴露、工作区策略、目标服务检查及操作授权；不推导其他成员的连接或整个协作空间权限。 |
| 用户电脑已连接Codex或开启Work Sync | 对应功能具有其自身连接 | Dot本地访问仍须明确允许；本地skills需连接到Dot的电脑，云浏览器登录也不随之迁移。 |
| 服务端明确拒绝某对象的读取 | 当前身份/请求的这次读取被拒绝 | 与目标相关的身份、范围或配置变化；不把拒绝推广到所有对象。 |
| Lody登录与机器目录查询通过 | Lody身份及这些查询可用 | 目标配置、模型认证与受控执行结果。 |
| 安装检查通过，Agent实际读过技能 | 该实例安装及对应读取有证据 | 若验证平台自动引导，还要有首次入口来源；业务成功另验。 |
| 历史spec9：正式ref/工作副本d27f1a0、插件0.2.0，bootstrap仅doctor通过 | 当时发布后的源码、依赖及检查入口有证据 | 当时缺旧boot基线；不将历史来源写成最新正式版本。 |
| 历史spec12：正式ed9096b/0.2.1；新内核启动晚于spec11实际观测，boot摘要不同；依赖、新私密身份及原历史/产物对账通过 | 不同内核上下文下可恢复原任务关联；该轮0新模型回合，对账时工作副本已开发0.2.2 | 当时readiness unknown不代替当前观测；准确VM/磁盘机制、Dot hook、独立新任务及首次送达未由此证实。 |
| 观察进程在准确回合running时退出，旧身份被清理；新身份按已保存refs观察到同回合继续运行并持久化完成 | 本地观察进程与身份丢失后可接续同一任务，未重发；新产物字节与摘要可核对 | 整个协调脚本、控制主机未因此重启；不证明结束通知完全未发生或直接读取远端FS。 |
| 清单指向包内setup技能，构建/移位/来源检查通过 | 本地分发入口和资源一致 | 安装扫描接受、平台run setup及新/既有对话调用分别验收；不能把配置文件当hook已触发。 |
| 一个远端配置完成受控任务 | 该配置与这些实测操作通过 | 其他配置、平台和高级操作各自的验证。 |
| 本轮子Agent完成独立审查 | 有另一上下文的审查结果 | 独立云任务仍需平台来源与初始化记录；共享文件系统不满足该证明。 |

“允许”“拒绝”“缺少工具”“运行失败”“未观察”分别报告。授权范围内的必要访问检查可以帮助消除未知，明确拒绝则停止相关操作。已有授权不因跨Agent分工而扩大，也无需因检查结果尚未知而重复索要同一授权。

## 初始化与恢复的设计原则

准备脚本、会话启动hook和实例/存储回收事件分别核实。优先让初始化动作可重复、可诊断，hook只负责在支持的时机调用它；不让任务恢复依赖重置前通知。当前正式托管配置在准备阶段调用`bootstrap --prepare`，启动指引要求读取技能并执行`--repair-missing`；后者只对明确缺少的受管依赖修复，不恢复模型任务或worker。

任务关联和必要成果在执行过程中按获授权的持久化目的地保存；本地marker、进程PID和同名路径不能证明跨重建保留。恢复时区分依赖重装、身份验证、业务会话对账和worker重启，不自动复制登录态、重复创建会话或承诺无法保证的恰好一次执行。

Dot主动Reset会删除Dot自身上下文、会话和计划任务，不能当作依赖修复步骤。另存的文件、Codex线程、ChatGPT会话按各自位置管理；这也不证明任意执行器的磁盘或进程会保留。周期存储回收及前后hook仍未取得官方证据，Codex会话hooks不构成这种证明，来源见[生命周期说明](environment-model.md#存储重置启动入口与hooks)。

## 架构评审清单

1. 能否对每次操作说明用户目标、Agent、工具连接与实际执行位置？模型服务位置是否被误当成命令位置？
2. 会话、任务、实例和主机是否分别识别？引用是否带系统和类型，绑定是否有时间与来源？
   Dot产品、它自己的云电脑和它发起的Codex任务环境是否仍分开记录？
3. 产品协作空间、执行器目录和Lody工作区是否各有资源与权限边界？
4. 发布配置、安装产物、实例应用、指引发现、实际读取和业务结果是否分别取证？
5. 是否分别记录用户授权、工具能力、运行约束和目标服务返回？未知是否有可行的范围内核验方式？
   是否承认已授予插件连接的跨产品共享，同时独立核对本地电脑访问、浏览器登录和CLI/模型身份？
6. 恢复或交接是否误包含活进程、连接、私密登录态或未取得的他人上下文？
7. 证据是否标明来源与适用范围，失败、拒绝和未观察是否分开？公开资料是否已脱敏？

若新方案改变实际模块边界、身份传递或发布机制，应按仓库对应的设计流程单独评审；本附录不代替这些决策。[原截图任务的来源与版本记录](fresh-task-acceptance.md#已有截图回执的补充)只解决对应的历史验收缺口；新版发布、当前读取与跨端结果各有自己的证据，不由文档完善替代实证。
