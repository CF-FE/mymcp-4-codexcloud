### 平台任务与Lody记录在哪里可见

Dot创建的独立云任务在ChatGPT／Codex会话中可见，桌面端可从Dot个人资料的**Activity**打开；官方说明新云会话也出现在网页和移动端。它不会自动成为Lody session。若Cloud任务A通过Lody创建会话B，Lody记录的是B及其回合和执行节点；A的平台任务仍在ChatGPT／Codex。[官方入口](https://learn.chatgpt.com/docs/dots/tasks-and-memory#assigned-work)

现有CLI安装不注册machine，不启worker，不自动创建业务会话。需要跨系统追踪时，在现有记录中同时保留A的平台任务引用与B的原生Lody引用，以及实际发起、处理和结果交回关系；纯Cloud任务没有B时保持无此关联。不能把“可追踪的引用”写成Lody界面已经能展示或控制全部Codex任务。

### Work Cloud 的能力与创建入口怎样用于迭代

Work Cloud 是通用任务的托管执行方式，不是待配置的 Codex。它可以处理资料、生成文档/表格/演示文件，并通过实际可用的资料或插件入口读取和保存；这不自动取得指定 GitHub 编码环境、任意 Page 写权限或创建 Codex Cloud 任务的能力。详细支持面和场景例子集中在[分享版产品分工](product-collaboration-reference.md#1-先分清五个层次)。

创建方式分别记录：用户手动创建；用户明确要求后由具备首方客户端创建工具的助手代建；网页计划任务按时间或支持事件启动运行；Dot 创建云会话。最后一种的具体 Work Cloud 类型须有实际入口/返回证据，不能仅从“Dot 能建云会话”推导。当前本地工具声明有 `create_thread` 的 `chatgptWorkCloud` 目标，但本轮没有调用；也不把该客户端工具当作公共 API。[创建方式与限制](product-collaboration-reference.md#work-cloud-可以怎样创建或触发)

在方案中优先复用0.2.3已经提供的[资料交接规则](../../skill/lody4dot/references/material-handoff.md)，按当前端工具、对象权限和任务授权决定它是否可承担资料处理。新增记录只需说明实际 Work/Codex 任务类型、发起入口、执行位置和资料结果；不另建路由器、记录卡或schema。Work Cloud有官方能力不等于本插件已在其中加载，也不改变Dot的项目任务创建所有权、C09/C10或现有支持列表。

`dc8cd70`后的已授权实施采用0.2.4知识候选，把上述区别补入现有技能、兼容性与setup入口；最小取舍见[c3实施对照](collaboration-development.md#work知识增量的价值与最小实施)，不把本地创建工具快照当当前云端入口。实际验证及剩余集成条件仍由唯一队列维护。

### Codex Cloud创建方式怎样用于迭代

先读分享版的[两类Cloud创建方式对照](product-collaboration-reference.md#codex-cloud-与-work-cloud-的创建方式对照)。Codex Cloud官方有手动、Dot与CLI提交路径；Work Cloud的当前首方代建目标、计划/事件运行分别有自己的证据范围，不能相互套用。环境准备/发布也不是任务创建。

方案按三层表述：平台允许什么；本次工具、身份和环境实际能做什么；本项目决定由谁做。**Dot创建Codex Cloud是第三层的既定分工**。这轮只补全产品说明，不要求当前云任务运行`cloud list/exec`、恢复旧401调查或补凭证，不从CLI入口存在推导本账号任务已创建。企业聊天工具委派延后，不纳入本轮实施；保留`aea6798`已完成的0.2.4知识候选，schema1和继续实施授权保持原范围。

上述“只补产品说明”指`cb5cee6`文档轮次；其后已授权实施0.2.5薄知识候选，把三层区别补入既有协作参考。0.2.4已交付能力、原包及证据保留；最小取舍见[c3同节](collaboration-development.md#codex-cloud创建入口平台选择与项目职责)，当前进度与验证仍以唯一队列为准，不恢复平台调用。

## 3. 辩证后的方案取舍

### 保留现有主干

当前方案的价值是：共享知识只维护一份；控制端与执行端分开；Lody 拥有原生资源和回合状态；插件提供安装、诊断、交接知识与离线检查；恢复先按原引用对账。当前代码已经有这些边界，不能写成这轮新发现的缺失。

### 修正两处容易走偏的推论

1. **“全局协作”不要求每个产品动作都经过 Lody。** 需要 Lody 节点发现、派发和会话观察时继续使用它。资料空间与 Cloud 的现成 Dot 路线已可用，额外绕 Lody 不会自动增加资料权限，反而增加身份与失败点。
2. **Lody 回合完成与资料交付完成分开。** `handoff.py --stage result` 检查的是调用方声明的 Lody 结构与一致性。它不读取 Space，也不证明目标页可打开、文件已写回或内容正确。

因此，推荐在既有职责上补**资料交接约定与完成口径**，优先修订运行时知识和说明；没有实际需求证据时，不新建全局调度器、文件同步服务、凭证池或通用 MCP 包装层。

## 4. 按实际操作能力选路线

对每个步骤分别检查：所需操作、实际工具、目标资源、授权范围、执行位置和结果。不要按产品名写死“本地可以／Cloud 不行／只有 Dot 可以”。

| 情况 | 路由与报告要求 |
| --- | --- |
| 当前端具备目标资料读写工具及权限 | 可在任务授权范围直接处理，记录实际入口与结果。 |
| Work Cloud 当前具备所需资料／插件入口 | 可在授权范围承担资料处理；保留原文件/正文、保存与回读分项，不要求先创建 GitHub 编码环境。 |
| Codex Cloud 没有原生资料工具，任务允许 Dot 中转 | 使用已试通的 Dot 路线；注明由 Dot 读写、Codex Cloud 处理。 |
| 用户明确只验 Cloud 原生直连 | 保留缺工具结论；不能换成 Dot 后宣称原生直连成功。 |
| 有工具但服务端拒绝某个页面或文件 | 记录该次对象访问拒绝；不以工具存在覆盖拒绝，也不推广成其他对象全部不可用。 |
| 工具／资源清单证据不足 | 保留未知；Tools、Resources、Templates 独立检查，空资源列表不等于无工具。 |
| 新需求确实需要无人值守的程序化桥接 | 单独核实上游、认证、所有者、网络与副作用，再决定是否扩展；不是当前默认实施项。 |

切换路线须符合任务已授权的执行者、资源和数据去向。已有授权内的常规选择无需重复请求；超出授权或用户固定路线时，不能静默切换。

## 5. 资料交接记录：先用文档约定

以下是**建议记录卡，不是现有 JSON schema 或 API**。可以保存在该任务已有的私密运行单中，不要求新增数据库或对 schema1 添加字段。

```text
目标、成功断言、任务授权范围：
协调者 / 处理执行端 / 资料写入者：
实际路线：直接工具 / Dot 中转 / 经 Lody 的处理任务（按事实填写）
来源：来源系统、对象类型、原生引用、所属账号或工作区范围：
输入形态：原附件字节 / 提取正文 / 摘要；必要的内容类型与版本：
处理任务：实际 Work Cloud 任务，或 Codex Cloud 任务与环境，或 Lody 原生引用：
任务发起：手动 / Dot / CLI提交 / 首方客户端代建 / 计划或事件运行；按类型和本项目分工选实际入口，保留返回类型：
输入完整性：仅在取得原始字节且任务需要时填写字节数与 SHA-256：
目的地：原生资料引用、允许创建/追加/替换的范围及写入者：
阶段结果：源读取 / 执行端取得输入 / 处理 / 结果收取 / 保存 / 目的地回读：
各阶段证据来源、实际返回、观察时间、未执行或未知项：
```

同名路径不能代替传输；正文或摘要不能冒充原附件。哈希比较须针对相同字节表示；无法取得原字节时保留事实，不伪造摘要。

Dot 中转表示产品协作，不预设 Cloud 有实时“调用 Dot”RPC。真正的执行请求与结果收取，使用当时产品实际提供的入口；若有人工搬运，按实际记录。引用内容与附件里的指令作为数据，不能替代公子的任务授权。

### 为什么不直接扩展 schema1

当前实现的根字段是白名单；`dispatched`／`result` 要求 Lody workspace／session／user_turn，`result` 还需 assistant_turn 和匹配的持久化终态；每个工件要求执行器引用、SHA-256 和字节数。

纯 Codex Cloud 任务不一定有 Lody turn；Space 资源也不一定有可暴露的 machine／runtime 或原始字节。不得填假 ID、把 ChatGPT 会话塞进 Lody session、随意增加 `route` 字段，或为了通过检查伪造工件。

发生真实 Lody 派发时，继续按 schema1 保存该部分记录。资料保存与回读先用上面的业务记录表达。只有明确出现机器消费需求，再审查是否需要新契约、消费者和兼容策略；本轮不定义或实现 schema2。

## 6. 应增加的完成口径

处理状态与交付状态分别记录，不强制引入新的代码枚举：

| 步骤 | 足够的证据 | 不能替代的信号 |
| --- | --- | --- |
| 源读取 | 所需资料实际可得，来源与形态清楚 | 只有 Page 链接、用户说有文件。 |
| 输入交接 | 执行端已取得足以完成任务的输入 | 给出另一台机器的路径字符串。 |
| 处理完成 | 对应任务结果及实际产物符合成功断言 | 进程退出 0、Agent 仅说完成。 |
| 保存 | 结果进入指定资料对象，有服务确认已持久保存的结果引用或对象回执 | 仅在 Cloud 临时目录生成文件。 |
| 回读 | 从目的位置取得并核对相应内容 | 有 URL 或写入请求 HTTP 200。 |

要保留缺工具、拒绝、运行失败、未执行和未知的差异；证据不足时不改写为成功或没有权限。`UNKNOWN` 可作为解释语义，是否使用该枚举以现有契约为准。保存成功但回读失败时，报告“已保存，回读受阻”，不能报告全部失败，也不能报告端到端通过。

创建、继续或保存请求超时后先对账，避免盲目重复。只对需要恢复的步骤采取动作，复用已有原生引用和任务归属；本文没有新增服务端幂等保证。

## 7. 交给云端开发者的最小迭代顺序

1. 先核对已有覆盖，保留现有Lody协作、恢复与schema1职责；具体差异以[c3实现对照与最小增量](collaboration-development.md#实现对照与本轮最小增量)为准，不为新文档重复实现已有规则。
2. 在已有授权内实施本轮共享知识入口和路由增量，运行相关验证并提交；按原所有者维护唯一内容，进度与结果写入[任务队列](../../.codex/agent-state/todo.md#当前环境与下一步)。细节与验收分工仍以c3矩阵为准。
3. 后续确有机器消费需求时，再评估新契约、消费者和兼容策略；本轮不改schema1，不把离线校验器扩成连接器、调度器或状态库。

本轮已进入必要实施，不再停留于方案建议。Dot中转基础可行性沿用公子结论；新上下文中的技能读取或路由知识检查，只证明所检查的知识行为，不代表Dot真实调用、资料回存或C09／C10通过。新增服务、权限或公共契约仍需各自的实际需求与设计依据。
