## 目标与范围

让 agent 能根据任务选择正确的 Lody 操作，发现当前版本的命令和能力，完成授权范围内的工作，并用实际结果判断成功或失败。以 Codex 云端作为首个安装目标，其他支持 shell 的 agent 环境可复用指引和命令参考。

“掌握一切用法”采用可验收的定义：覆盖已核实版本的全部公开一级命令，为子命令建立可追溯索引；常用任务提供经过验证的流程，长尾操作按需查询当前版本帮助。新版本、未知参数或不可用能力必须识别并查证，不能以静态文档保证永久完整。

2026-10-20 用户已授权在本对话持续实施。安装、加载、账户和任务验收分别记录；不创建占位 MCP，不把缺少前提的真实验收当作已通过。

## 已核实的依据与缺口

研究基线为 2026-10-20 取得的 npm `lody@0.107.2` 发布物，下载内容与 registry 提供的 SHA-512 SRI 一致。已读取包内 README、package.json，并静态检查 CLI 命令注册及 MCP 相关实现。后续运行与依赖验证见任务队列关联的记录。官网 CLI 文档与快速开始现已成功读取，并交叉确认包名、Node 要求和无头登录入口。

| 已知事实 | 对方案的影响 |
| --- | --- |
| CLI 注册了 20 类公开一级命令 | 覆盖表应遍历真实命令树，而非只整理几个示例 |
| Lody 已有会话、发现、operation、调度等内置 MCP 能力 | 优先复用已有能力，不先重写全量 MCP 包装 |
| 内置 MCP 需要 Lody 注入 workspace、machine、session 等上下文 | 内部启动入口不能直接作为通用外部 MCP 安装接口 |
| Node 要求为 `>=22.14.0 <23 \|\| >=23.6.0`；当前云机为 `24.19.0` | 当前 Node 版本符合声明，但仍需验证原生依赖和实际启动 |
| 依赖包含 `better-sqlite3`、PTY 与 keyring 模块 | 无桌面 Linux 的安装与凭证存储不能仅凭 Node 版本判定可用 |
| 2026-10-20采集时`next`为`0.94.1`，`latest`为`0.107.2` | 默认安装使用可复现锁定输入；标签是当时事实，运行时不因Lody版本差异拒绝执行，更新查询须显式请求 |
| 支持 `LODY_DATA_DIR`，登录有 device authorization 和 `--auth` 入口 | 可设计无桌面授权流程及独立状态目录，仍需真实验证 |
| 此 npm 构建的平台选择固定为 cloud | 不承诺设置一个环境变量就能变成 OSS 构建 |
| 官网明确 `--help` 是参数与位置参数的权威来源 | 缓存参考用于导航，实际参数仍以所用版本帮助为准 |
| 官网概括 create/chat/cancel 需要本机进程；0.107.2源码及后续实测支持直接派发已有远端Agent | 区分控制端与执行端，按实际目标确定daemon要求 |

用户指定的 [官网 CLI 文档](https://lody.ai/zh/docs/cli/) 和 [快速开始](https://lody.ai/zh/docs/quickstart/) 均已返回 HTTP 200。快速开始使用 `npx lody daemon start`，与所研究的 npm 包名对应；Node 版本要求也一致。官网、发布物和未来实际帮助输出应一起维护，不能只依赖其中一份资料。SRI 校验只证明下载内容与 registry 一致，不代表所有运行行为已经验证。

## 方案的辩证比较

| 形式 | 能解决的问题 | 单独采用的不足 | 本方案选择 |
| --- | --- | --- | --- |
| 一个很长的 skill | 容易分发，能解释操作语义 | 容易过时，占用上下文，不能证明命令真的可用 | 使用简短入口与按需参考 |
| CLI 辅助脚本 | 版本探测、环境诊断和重复安装可自动验证 | 不能独自教会任务拆解与上下文判断 | 仅实现确有必要的安装与诊断逻辑 |
| Lody 已有 MCP | 结构化调用，复用现有资源和会话能力 | 依赖宿主上下文；工具 schema 不足以解释完整工作流 | 检测到受支持的注入后使用 |
| 自建全量 MCP | 能统一暴露 CLI 操作 | 重复已有功能，并需维护权限、状态与版本映射 | 首版不做；出现具体缺口后单独评估 |
| 自建常驻服务或控制台 | 可管理长期连接、任务和状态 | 重复 Lody 职责，云任务生命周期又增加维护成本 | 不作为插件自身组件 |
| 组合分发插件 | 能把指引、参考、辅助工具和环境配置一起交付 | 需要验证包内资源和目标平台加载方式 | 采用，插件名 `lody4dot` |

推荐组成：任务指引、版本化命令参考、少量安装/诊断工具、Codex 云环境启动说明，以及可选的现有 Lody MCP 接入。执行优先使用当前环境已验证的 CLI 或工具，不强制所有功能都经过一种接口。

最强的反对意见是：功能全面就意味着同时维护大量说明、脚本与 MCP。改进方式是把命令事实和操作流程分开：命令参数从对应版本帮助与资料建立索引，技能只维护选择规则和工作流；辅助脚本不再重写 session、schedule 等业务 API。

详细开发前的辩证修订：命令覆盖与 agent 任务能力分别验收；最小加载入口提前验证；查询控制端与任务执行绑定不同运行前提；安装采用锁定输入和失败恢复；安装、只读诊断和显式认证分开。完整质疑、证据与任务映射见开发方案第 2 节，不将这些计划条件当作已运行结果。

## 组成与仓库归属

以下为源码与分发的职责布局：

```text
skill/lody4dot/
  SKILL.md                 # 任务入口、能力发现、版本判断、执行与结果核验
  references/              # 命令索引、主题用法、来源、兼容性与故障处理
plugin/lody4dot/
  README.md                # 交付内容、安装入口和支持范围
  scripts/                 # 安装、唯一诊断、显式认证和分发构建
  runtime/                 # 独立manifest、锁文件和禁用安装脚本策略
  .codex-plugin/plugin.json # 核实后的原生清单；包内skills由构建收集
tests/lody4dot/             # 安装、诊断、分发完整性与任务场景验证
dist/lody4dot/              # 生成的自包含交付产物，不作为第二份源码提交
```

skill 是操作知识的唯一维护位置，plugin 负责交付与安装。构建时收集技能和资源，不依赖指向包外的符号链接。首版没有 `mcp/lody4dot/`；只有已证实的外部接入缺口才可能引入适配器。

## 能力覆盖与教学重点

| 主题 | 基线公开命令 | 指引需要教会的行为 |
| --- | --- | --- |
| 登录与运行 | `login`、`logout`、`start`、`app`、`daemon` | 识别已登录、运行进程和真实就绪的区别；识别桌面功能限制 |
| 资源与配置 | `workspace`、`machine`、`project`、`agent-config`、`agent-role`、`mcp`、`github` | 先发现和选择目标，再验证配置；区分本机与工作区资源 |
| 会话与任务 | `session`、`schedule`、`operation` | 创建、观察、继续、取消和验证结果；正确理解异步与提议状态 |
| 同步与交付 | `sync`、`export`、`migrate`、`review`、`feedback` | 根据平台、输入和授权选择流程，区分本地文件与远端状态 |

首版指引必须包含这些实际语义：

- Role 会覆盖部分手工 machine、agent、mode、model 等配置，不能把被覆盖参数当成最终配置。
- 目录结果分页；完整枚举需继续 cursor 或使用支持的 `--all-pages`，不能把第一页当全集。
- `--json`/`--jsonl` 的 stdout 用于结构化结果，诊断信息从 stderr 读取；不按自然语言输出猜状态。
- MCP 已选择不代表已加载；资源可用性的缓存观察不代表派发成功。
- Role 和 schedule 的提议不等于已保存或已创建；以操作的实际返回状态为准。
- `operation list` 针对本机 store，且需要 requester session，不能充当所有远端机器的任务总表。
- 创建会话后按照通知与观察契约等待结果，避免无意义轮询或重复创建。
- `agent-config show` 默认隐藏环境值；不默认使用 `--show-secrets`。
- 复用 `lody review prompt` 等已经存在的指引入口，不复制一份长期漂移的完整提示词。
- 区分 cloud 与 OSS 的能力；桌面应用、模拟器和预览等依赖按实际运行平台标记。

日常执行遵循“识别版本与上下文 → 发现目标和能力 → 选择流程 → 执行 → 核验结果”。保留已有任务授权，不为每条命令重复确认；也不把获得插件当作创建新任务、修改资源或扩大权限的授权。

## Codex 云端安装方案

### 两种运行模式

默认先支持云端作为控制端：在 Codex 云环境加载 `lody4dot` 并运行 CLI，发现用户已授权的 Lody 工作区、机器和会话，查询与观察结果。官网明确 `session list/history/observe/show/rename/archive/restore/delete` 不要求本机运行进程，但需要登录与工作区权限；这些操作的副作用仍须遵守任务授权。

后续0.107.2源码与真实派发纠正了官网的概括：`session create/chat/cancel` 可由控制端公开CLI直接操作已授权的在线远端machine/config，无需控制端本机daemon；执行端仍需运行进程与底层Agent凭证。当前机器执行及 `agent-config refresh-capabilities` 才需本机运行前提。只有真实派发、持久化结果与产物核对才能证明相应任务能力；不从token或在线目录单独推导成功。

云端自身作为长期执行节点是后续可选能力：需要注册机器、运行 daemon 和 agent，并验证进程重启、机器状态与任务恢复。首版受控任务可复用已有远端Agent，执行端进程仍须可用。安装 CLI 不自动建立执行能力，也不能将一次性云任务承诺为永久在线机器。

### 安装与启动职责

1. 预检：只读检测 Node、平台、可写位置、代理与 CA，以及原生模块所需构建条件，输出缺失项。
2. 可复现输入：以`0.107.2`为知识与默认安装基线，记录实际解析的依赖锁定结果。先检查依赖安装脚本，再允许最少必要的原生构建，保留TLS与完整性验证。已安装Lody版本不同或无法探测只告警，不据此重装、升级或阻塞业务；按实际帮助与执行结果核实所需能力。
3. 稳定安装：依赖放在 checkout 之外的可写工具目录，例如 `/workspace/.tools/lody4dot/`；使用稳定的绝对启动入口，不登记临时 `_npx` 缓存路径，不改 `HOME`。
4. 分离状态：使用受支持的 `LODY_DATA_DIR` 管理任务状态。依赖可以进入环境快照；用户登录态不得进入共享发布物或共享环境快照。私密状态目录、跨任务恢复和 keyring 行为须由实际平台能力确认，目录名称本身不提供隔离保证。
5. 加载插件：核实 Codex 原生插件清单与注册方式后使用其正式入口。在当前云配置流程中，可通过 `start_skill` 明确加载操作指引和运行诊断；它与原生插件注册是两种接入方式，必须报告实际采用哪一种。仅恢复仓库文件不能算加载成功。
6. 运行时授权：任务开始后使用受支持的设备授权或凭证通道登录，检查目标身份与 workspace。云代理的凭证占位符不自动等同可存入 Lody 本地登录状态的真实凭证；不把凭证写入仓库、日志或安装脚本。
7. 启动和验证：需要 daemon 的操作，在任务启动时显式恢复并检查就绪。文件和依赖保留不代表进程保留；升级后核对运行中进程版本，不仅检查 npm 安装结果。

安装必须可重复执行，保留现有用户配置，明确报告变化；停止操作只管理安装流程自身启动的进程。使用现有隔离 checkout，不另建 Git worktree。

### 凭证入口

用户已选用全局环境变量 `LODY_CLI_TOKEN` 提供凭证，`lody4dot` 复用此名称，不再要求另一份 token。它是本插件的接入约定，不假定 Lody CLI 会自动读取该变量；登录适配器需通过核实过的授权入口使用它。不得把值写进源码、配置示例、日志或分发包。

诊断仅区分变量未注入、变量已存在、授权已验证，不能把“变量存在”直接报告成登录成功。全局配置与当前运行任务分开检查；若任务尚未收到变量，待配置传播或后续任务启动后复查，不能据此要求用户在聊天中重新提供凭证。凭证是否是可直接用于本地授权的材料，还需与云平台的注入方式一起验证。

### 网络与配置

`lody.ai` 的允许规则现已发布，并在当前实例观测为已生效；官网请求已成功返回 HTTP 200。判断运行网络是否更新，应核对当前生效规则与实际请求；来源配置版本号仍旧不变，不能单独作为必须新建或切换任务的依据。

包内静态配置还涉及 `convex.lody.ai`、`backend.lody.ai`、`api.lody.ai`。实现阶段按实际连接需求申请准确目的地，保留已有规则，不直接放宽为全网。仅放行官网不足以验证 CLI 连接。代理、CA、WebSocket/长连接及额外资源下载均需实测，不能绕过代理或关闭证书验证解决。

## 实施顺序与验收

| 阶段 | 交付 | 完成条件 |
| --- | --- | --- |
| A：来源与契约 | 官网核对、版本与命令覆盖表、Codex 加载方式、最小连接前提 | 20 类公开命令有来源定位；内部入口不冒充公开 API；包名和发布渠道已交叉确认 |
| B：最小插件 | 核心技能、按需参考、安装与诊断工具、自包含产物 | 干净云环境可重复安装；能正确报告未登录/不支持状态；新任务能加载指引 |
| C：真实闭环 | 指定 workspace 与机器的任务演练 | 从发现目标到操作、观察和结果核验完成；区分失败、待确认、进行中和成功 |
| D：扩展覆盖 | 高级调度、迁移、同步、评审、可选云端执行节点 | 每项能力有独立场景和平台边界，不能用部分场景通过宣称全部已验证 |

先做 B 与 C 的常用闭环，再增加 D 的深度；A 中的完整命令索引保证长尾功能仍可发现。C 的真实执行要求可用账户和指定测试目标，未满足时只报告独立完成的部分。

建议行为测试场景：未安装、版本差异或探测失败只告警、显式更新查询失败只告警、默认离线、未登录、错误workspace、分页结果、Role覆盖参数、提议未落地、MCP上下文缺失、重复安装、进程未实际升级，以及任务成功/失败/取消。安装与诊断逻辑用隔离目录和可控CLI fixture验证；能力事实再对照实际版本帮助；真实集成测试单独记录，不能拿mock通过冒充。

实施中可用的探测命令包括 `lody --version`、`lody --help`、`lody session --help` 和 `lody daemon status`。具有真实身份与授权目标后，按已核实参数执行例如 `lody machine list --workspace <workspace> --all-pages --json` 的只读查询。这些命令用于说明验证目的，不代表全部已运行；实际命令、结果与未执行项见验证记录和插件 README。

文档用中文解释，命令和字段保留原拼写；不把示例标记成已执行结果。辅助脚本复用仓库已有的简单风格与结构化诊断，避免新服务框架。维护兼容版本、来源日期、覆盖状态与变更记录；升级时复核命令树和关键场景，不自动跟随任意 dist-tag。
