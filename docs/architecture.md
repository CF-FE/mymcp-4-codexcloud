# 仓库结构与迁移约定

## 目标与证据

仓库用于维护 Codex 云端可使用的插件集合。用户提出 `mcp / skill / plugin` 三部分划分，并要求审视后推进实现。执行时仓库没有提交或应用文件；已有插件位于当前会话无法读取的协作空间中。

这支持先建立清晰的维护边界，但不足以确定语言工具链、插件清单格式或云端启动命令。

## 对三部分划分的审视

成立的部分：按能力形态导航，方便分别查找服务、技能和安装入口，也保留了用户提出的三部分结构。

主要张力：三者并非互斥。一个插件可能携带 MCP 和 skills，如果把所有内容重复放到 `plugin/`，后续修复会产生多个源码版本；如果无视原插件的资源路径直接拆分，则可能破坏安装和执行。

采用的方案：两个能力源码目录加一个组合分发目录。每份能力有唯一维护位置；插件通过明确的组合说明以及后续核实的打包配置使用能力。发布产物可包含构建生成的副本，但不单独修改副本。

## 目录与关系

```text
mymcp-4-codexcloud/
├── mcp/                  # mcp/<id>/：服务源码与运行说明
├── skill/                # skill/<id>/：SKILL.md 与随附资源
├── plugin/               # plugin/<id>/：组合说明及分发定义
├── docs/                 # 共享设计与迁移说明
├── scripts/              # 仓库结构检查，不包含插件实现
├── tests/                # 结构检查工具的行为测试
├── AGENTS.md             # 给后续代理的简短开发约定
└── README.md             # 项目导航和验证状态
```

`plugin → mcp / skill` 表示分发组合关系，不是所有条目必须安装全部能力。skill 可以要求特定 MCP 能力，此要求需显式记录。MCP 实现不反向依赖插件打包目录。

这种结构增加了打包时收集资源的工作，换来单一源码维护位置。没有真实包之前，不先引入通用打包框架、统一运行时、插件市场索引或没有实际目标的 CI。首个插件应检验这些边界是否适合项目。

当前结构检查工具只使用 Python 标准库，检查必需文档、条目命名和入口，并拒绝条目与入口的符号链接。它不校验目标平台的插件清单或实际运行行为，允许当前零条目的骨架存在。工具使用 Python 不约束后续 MCP 的实现语言。

## 导入已有插件

1. 取得「协作空间 → 插件集合」的完整源文件，包含隐藏清单、资源、脚本、依赖锁文件和许可说明；迁移验证完成前保留原文件。
2. 检查内容并排除真实凭证、运行缓存和生成产物，记录原目录布局与可执行文件权限。不要把隐藏文件一律忽略，也不要把凭证带入仓库。
3. 阅读实际清单、`SKILL.md`、源码及相对路径引用，识别它包含的服务和技能。先将完整插件放入 `plugin/<id>/`，保留其可运行布局。
4. 若能在保持行为的前提下独立维护，再将能力源码移入 `mcp/<id>/` 或 `skill/<id>/`，并更新经核实的打包定义；检查必需文件和权限均已保留。不能安全拆分时，保留完整插件并说明原因。
5. 用已有锁文件安装依赖，在云端验证插件安装、技能加载和代表性的 MCP 请求；没有涉及的能力无需增加虚假验证。
6. 检查分发产物中的清单和资源，确认安装后不依赖仓库之外的文件或符号链接。在首页补充实际条目及通过、失败、跳过的验证结果。

## 下一项能改变决策的验证

导入第一个真实插件，并验证它的安装产物能找到全部所需能力和资源。若它的格式要求不同的布局，以保留实际功能为先，再修订组合方式。只有这个验证完成后，才能声明插件已经迁移并在云端可用。
