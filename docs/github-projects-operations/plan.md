# Projects协作边界与通用操作方案

2026-10-28，方案v1.1。公子已明确：ChatGPT云端和Lody均已接入GitHub Projects MCP；组织参与者在既定授权范围内可直接list/read，write需要收敛，并优先以正式看板记录对齐工作。两端实测支持具体操作路径，不代表所有会话均有相同账号权限。操作技能1.0.0已取得固定提交的文件接入、实际读取及Dot指定对象只读回执；当前1.1.0补齐统一入口、事件关联与补写处理，正式看板切换、写者任命及各端新版读取仍分别取证。

## 取舍与分层

全员经记录者读取会形成不必要的中转、等待和摘要失真；全员持有工具后自由改状态又会使事实、决定和验收互相覆盖。采用**范围内直接读取、业务决定有明确责任人、正式记录按对象单写**，保持并行与可追溯性。

各角色以正式Project及关联任务、有效回执为统一工作入口：接单、跟进、交接和判断下一步先定向查询，不另抄一份全局进度。看板负责集中理解当前工作，详细证据通过链接展开；统一入口不等于一个字段能替代全部事实。聊天是提报通道；缺项、滞后或冲突先显式标记，由当前写者核原生证据和生效决定后补写，不能用旧看板值否定已经发生的事实。未完成切换的任务仍使用原正式入口。

公子的新指令、权限撤销和当前安全约束立即约束相应动作，再补入正式入口；“以看板为准”不允许用尚未更新的旧值继续已被禁止的动作，也不把用户明确决定降格为需要重新批准的普通提报。

| 层次 | 唯一维护内容 | 使用方式 |
| --- | --- | --- |
| 组织协作 | 责任、汇报、决定、派发、验收、接管和流程审计 | 复用organization-collaboration及有效任务上下文，不在操作skill复制岗位定义 |
| Projects操作 | 工具选择、字段与ID、分页、写后回读、部分结果和已知异常 | github-projects-operations；只有实际操作时按需加载 |
| 组织／项目实例 | owner、正式看板、Issue路由、当前写者、工具连接及实测范围 | 沿已有正式记录维护，不写死到通用技能 |
| 宿主与GitHub权限 | 实际账号、允许工具和源资源ACL | 可信配置控制；skill文字不冒充服务端权限隔离 |

第一版不复制MCP SDK、认证或传输代码。可选日期脚本仅处理已发现的具体迭代输入问题；不建立新的业务数据库、常驻记录服务或自动派发器。

## 统一入口与记录归属

| 信息 | 唯一维护位置／依据 | 从看板怎样取得 |
| --- | --- | --- |
| 项目目标、负责人、正式入口及关键决定 | 现有项目正式记录；重大事件关联受影响任务 | Project项目说明或约定的项目索引引用 |
| 任务目标、范围、分工、输入与验收约定 | Issue正文或已指定的受控任务记录，变更保留依据 | 条目关联原任务，不复制另一份合同 |
| 当前协作阶段、下一责任方 | 正式Project字段，依据明确的任务版本与事件 | 读取所需字段和对应有效依据；不是按最后评论判定 |
| 承接、进展、阻塞、变化与历史补录 | Issue评论时间线或受控事件记录 | 摘要与准确事件引用；保留发生与登记时间 |
| 实际运行、请求与执行轮次 | 原执行系统及其观察回执 | 沿任务保存的原生引用定向核对，保留UNKNOWN |
| 产物、检查、负责人验收与遗留 | 精确版本的产物索引、各自回执及承接记录 | 从条目展开对应证据，原件留在所在端 |

一个成果使用唯一任务引用，可关联必要的多次执行；每次独立委派留可定位的分工与执行关联，普通工具调用和实现步骤不逐条建Issue。项目级范围、负责人、环境或关键输入变化保留事件并关联受影响任务，不把项目事件仅藏在单个执行会话中。

事件使用原生评论／回执或受控记录引用，记操作者与登记者、发生时间、必要观察时间、登记时间、对象／版本／执行关联、实际动作和证据、下一责任人。更正追加并引用原事件；补录不伪装为当时已登记，未知不填造。可复用既有字段，不引入全局序号、事件数据库或逐条全字段填表。

职责和调用路线见[协作图](diagrams/access-and-recording.svg)，查询／写入与未知结果处理见[操作流程图](diagrams/operation-flow.svg)；对应Mermaid唯一图源及再生成方式见[维护说明](diagrams/README.md)。

## 操作边界

| 动作 | 依据／决定来源 | 实际操作者 |
| --- | --- | --- |
| list/read | 已授权读取范围和本次信息需求 | 各参与者直接查询；无需记录者批准 |
| 开工、阻塞、产物提交等事实 | 原执行者的版本化证据 | 当前写者按预授权规则登记，不逐笔找负责人批准 |
| 质量检查结果 | 实际检查者的方法、覆盖及结论 | 当前写者保留来源；不改写未验为通过 |
| 创建／关联任务、分配、优先级、日期、范围与依赖变更 | 项目负责人；组织事项由Dot在其权限内决定 | 对应目标的当前写者 |
| 完成验收、取消、重开及重复处置 | 正式负责人及有效依据 | 当前写者核一致性后登记；取消不等于质量通过 |
| 共享字段定义、选项、视图、工作流和看板结构 | 获授权的看板管理责任人 | 指定维护者；条目写权不覆盖共享结构 |
| 权限／可见性、整体删除等动作 | 相应明确授权 | 有实际能力的维护者；当前工具未暴露的动作不虚构入口 |

授权记录者仍是executor可承担的职责，负责人可兼任，不为记录职责增设岗位。小任务可由负责人同回合决定并登记；多任务按独立Issue／条目委派写者，避免全组织串行。共享Project里的不同业务项目可以有各自条目写者，共享字段和视图则统一维护。

同一条目同一时刻只有一个当前写者。委派期间负责人负责决定，由受委派者登记；亲自操作时先明确接回写权。子任务写权不覆盖父任务关闭、其他项目分工或依赖放行；新旧写者交接原请求、已成功部分、UNKNOWN及原生Cloud引用，不能以接管为由重建或重派。

Issue评论也是外部写入。执行者和QA默认沿原通道交事实／报告；确有需要时可预授权“指定Issue追加本人事实评论”，不连带获得改正文、状态、他人评论或关闭权限。不同报告可以并存，但版本和来源不得被摘要覆盖。

新增组织岗位`auditor`只核流程关联与整改证据，职责、独立性、报告路线及验收边界以[组织审计正文](../../skill/organization-collaboration/references/auditor.md)为准。它不成为另一位Project状态写者；登记审计发现也需相应写入授权。项目负责人仍负责业务验收，记录者核一致性，专业reviewer核产物质量，不用一次审计代替三者。

## 权限如何落地

读者优先选择只读连接或宿主实际支持的写工具禁用配置；写者使用明确覆盖目标的写连接。官方`/readonly`限制该连接提供的工具，不是按AI岗位配置的GitHub ACL。若全员共享同一有写权账号和完整工具集，按岗位限制主要仍是协作约定，不能称为技术隔离。

账号对Project及源仓库的访问、连接配置、本次任务授权分别核对。只有实际失败、目标或绑定变化时补必要检查，不每轮读取重验全部权限。现成有效预授权可复用；新权限、跨范围操作和拒绝后的恢复沿原授权流程处理。测试成功不产生未来业务写入授权。

CF-FE是本组织默认，项目已有GitHub仓库则Issue优先落在项目仓库，否则候选为环境仓库；两条路由都先核实际可见性和内容授权。私有Project不会使公开Issue私密，连任务存在性或引用都不能公开时，沿已有受控入口保留记录，等待合适的私有落点，不自动建公开占位项。内部会话、身份和素材仍留受控记录，必要检查者的引用访问能力另核。主看板、旧任务映射和切换点要明确；测试#3/#4不是正式主看板的默认选择，具体已创建看板及接入事实只在[组织适配](../organization-collaboration/github-projects.md)维护。

## 操作skill的最短路径

1. 从当前任务指定的正式看板及关联任务复用准确目标、授权和对象引用；缺项才定向发现。
2. 查询用get或带筛选的list，显式请求所需字段。只有需要全量结论时完成相关分页。
3. 写入核当前写者、业务依据、当前值及影响范围，执行最小变更。
4. 按返回ID独立回读；批量按项核结果，部分成功保留，UNKNOWN先对账。
5. 用短结果报告实际完成、缺项和下一责任人；需要交接或验收时附观察时间与覆盖。

常见“查一个任务的进度”不读取全方法手册，不额外询问写入授权，也不运行脚本。字段名已明确且支持名称解析时直接读；需要选项或有歧义再读元数据。查询按需进行，统一跟进责任人安排必要巡检，不让所有角色重复轮询同一看板。

## 派发关联、部分成功与审计

采用GitHub前置登记的任务，先核范围、授权、负责人验收归属及重复／未决请求，取得任务和Project条目准确关联并回读，再交实际派发者；本操作skill不派发Cloud／Lody任务。派发意图只证明准备动作，恢复时区分有证据未调用、调用结果UNKNOWN及已返回原生引用，不因一次空查询而再次创建。

原生执行已创建而登记失败，保留真实ID、轮次、版本、已成功动作及待补写对象，由原责任人在获准回报入口留待办；恢复后只补缺失部分。事件评论成功而字段失败、Issue关闭成功而Project同步失败也如此。待补写不撤销有效业务证据，但必须标明看板同步未完成；UNKNOWN先对账、不重发评论、不整批重放、不重建执行。迟到V1只进V1历史，取消决定与原生UNKNOWN分列，遗留带承接人、解除条件和后续引用。

审计查询先限定项目、时间窗及获准来源，对照需求／指令、原生派发执行、正式任务、产物验收与遗留；覆盖约定范围的关闭、取消、迁出及未决派发。只读看板不能证明没有未登记执行，权限或来源不足记未验／覆盖不足。关联核对与证据抽查分开说明，普通记录更新不因审计而追加逐笔批准。发现、整改、独立复核沿原任务和[追溯模板](../../skill/organization-collaboration/references/task-traceability.md)关联，不新建竞争的项目状态表。

## 双端证据对设计的修正

- 两端20方法均有成功路径，仍保留Lody的默认迭代异常；明确列表是兼容路径，不能记作上游已修复。
- 顶层start_date仍需提供；全部周期输入在创建前检查。固定上游实现可能先建字段再配置，失败先对账，不盲目重试创建。
- 新入板条目可能已为Done，实际原因未独立确认；先读基线，不自动清空或纠正。
- 安全审批拦截、服务端403、关闭对象错误可能都被外层INVALID_ARGUMENT包装；保留真实发生层和底层原因。
- ChatGPT云端已测两个不同条目批量成功；Lody已测单条批量迭代赋值／清空。未验的部分失败、UNKNOWN、并发与大批量不能合并成已通过。
- 工具当前缺少关闭／删除Project、删除字段及状态更新的方法。测试前明确保留策略，清理只处理本轮获准对象；不用额外删除权限消除报告中的遗留项。

完整覆盖矩阵与残留清单只有[合并验证记录](validation.md)维护。通用技能保留影响决策的已知行为，不携带完整历史日志、真实测试ID或特定通知目标。

## 交付与接入顺序

| 阶段 | 产出与验收 | 边界 |
| --- | --- | --- |
| 本地源码与证据 | 短入口、三份按需参考、可选日期脚本、双端合并报告 | 已验证接口事实与建议的恢复策略分开 |
| 离线验证与分发 | 日期测试、独立上下文走查、自包含ZIP与逐文件摘要 | 不复跑已完成的真实20方法，不冒充端侧已加载 |
| 目标端接入 | 用各端实际技能入口放置／安装，确认该版本实际读取及代表性查询 | MCP已安装不替代skill读取；不要求所有端同时升级 |
| 正式记录切换 | 指定正式Project、可见性合适的任务落点、写者、本次已安排审计时的审计绑定与切换点，沿已有获准任务核关联／回读 | 保留原队列历史与在途引用；已切任务停止旧状态双写，未切任务保持原入口，不为验收重派业务 |
| 后续改进 | 仅按新增需求或真实失败补测试、参数参考与规则 | 上游异常对应分支有新证据后才关闭，不用字数推算性能 |

首次行为走查至少覆盖准确引用只读、字段未返回、已有写授权、旧版报告、部分批量UNKNOWN、默认迭代缺口、安全审批拒绝和已有创建副作用。正式集成优先用已有授权对象的最小场景；没有写入需求时只验读取和正确拒绝无依据的写请求，不为验skill新建测试板。

1.1.0新增的行为走查覆盖：统一入口与聊天冲突、原生已建但登记失败、意图与UNKNOWN区分、历史补录、遗漏执行审计、私密路由及取消后未知运行。检查实际选择与拒绝的动作，不以包含某个关键词判通过；离线走查不冒充真实GitHub故障恢复或跨端接入成功。

读取路线更新不要求旧业务重跑；在途采用的技能／协议版本继续记录，公子新指令及权限撤销立即约束相关操作。涉及既有组织规范的进一步文字收敛应单独版本化，不借发布操作skill静默修改岗位和验收责任。

## 效率评价

以同一目标和相同证据要求比较必要工具调用数、重复全量发现、字段漏读补查、未知结果误重试及实际耗时。准确ID查询、同一看板字段复用、定向回读应减少重复调用；不预设固定提效比例。按需加载可量化读取量，但不能由字符数推算模型延迟或业务吞吐。
