# lody4dot 多宿主协作开发方案

版次：c1，2026-10-21。状态：开发交接提案；用户目标已明确，宿主接口与下列技术建议按证据收敛。本轮交付文档和指引修正，不将计划条件写成已实现能力。

## 1. 目标、依据与完成定义

目标：**同一份lody4dot能力可以在Dot、Codex云端及本地Agent宿主加载或安装，通过Lody服务发现目标、派发任务、交接上下文、观察结果并协作交付。** Dot按用户最新说明指ChatGPT云服务，独立于Agent主体；其官方产品标识和扩展接口尚待核实。

依据按职责区分：[r2产品方案](lody4dot-plan.md)与[d1开发契约](lody4dot-development.md)继续解释当前实现及T01–T12；[环境指引](lody4dot-environment-model.md)和[设计参考](lody4dot-environment-design.md)提供术语与证据边界；本方案定义新目标的候选范围和C01–C10任务卡，实际状态仅由[任务队列](../.codex/agent-state/todo.md)维护。新提案不提前关闭T09/T12，也不自动升级正式环境。

三层交付分别确认，最终目标包含第三层：

| 交付层 | 可验收的结果 | 适用限制 |
| --- | --- | --- |
| 基础安装 | 每个列入支持的宿主能找到并实际读取共享技能，使用已验证的工具入口，报告准确版本与角色 | 知识可读、工具可用和执行能力分项记录 |
| 双端协作 | 两个真实独立宿主经Lody面向同一授权任务协作，执行端产物被另一控制端复验 | 同实例子Agent、mock或目录存在不能替代跨端证据 |
| 含Dot多端协作 | Dot经实际支持的工具参与派发或结果交接，本地/云执行节点承担任务，另一宿主复验同一成果 | 人工传递回执只能报告人工交接；全自动闭环须有各端真实调用与回传入口 |

首轮使用自有临时数据和已有授权节点，保持一个协调写入者、一个产物写入者及只读复验者。新增worker、其他操作系统和MCP适配按前提扩展；不以完成部分安装替代整个协作目标。

## 2. 辩证结论与技术路线

保留已有“短技能、按需参考、原生CLI、少量安装诊断工具”的方向；增加宿主接入和协作交接能力。Lody继续拥有资源、会话和业务执行状态，lody4dot负责让各宿主正确使用这些能力。

已有事实支持以下近期优化：`compatibility.md`仍有“不推导取消已通过”的旧措辞，而会话参考和支持矩阵已有自有普通回合取消证据；命令索引的`local_runtime:false`缺少清楚的控制端参照说明；doctor早期异常会丢失已完成检查；build/install收据各自存在，诊断尚未汇总来源。这些是增量修订，不应重复开发已经具备的锁定安装、分页或脱敏工具。

| 候选做法 | 成立之处 | 最强反例或代价 | 本方案采用的修订 |
| --- | --- | --- | --- |
| 只扩充命令说明 | 能补知识盲点 | 已有20根/70路径导航，更多文字不能解决跨端输入、身份与结果关联 | 优先补协作流程、上下文与验收，长尾仍查对应版本帮助 |
| 所有宿主使用同一个安装包和清单 | 共享源码便于维护 | 技能格式、工具、OS和受保护路径不同；当前安装器仅支持Linux | 共享知识核心，按已核实宿主生成薄接入材料；平台安装能力单独验证 |
| 所有端都启动daemon | 能把机器作为候选执行节点 | 云控制端不需要daemon；host可能覆盖账户全部工作区，临时云机也不保证长期存活 | 安装、控制、执行角色分开，默认只准备依赖；worker按明确需要单独启用 |
| 全量MCP包装作为统一接口 | 无shell宿主可能需要结构化工具 | 重复已有能力，增加认证映射、业务语义与服务运维成本 | CLI可用端先复用CLI；Dot先验已有对外工具，无合法入口时才评估最小MCP适配 |
| 仅靠重置hook重新初始化 | 若事件可靠可自动触发 | 突发回收可能没有退出通知，现有会话hook也不是存储事件 | 幂等准备、入口检查、执行中保存与恢复对账共同工作；hook只是可选触发器 |
| 两端自动抢占和重试任务 | 故障时看似能快速接管 | 当前未证实服务端幂等键或分布式租约，create超时可能已受理 | 首版单协调写入者，未知先对账；跨端接管显式交接，不承诺恰好一次执行 |
| 所有账号共享一个登录目录 | 接入看似简单 | 混淆宿主身份和模型认证，登录态可能进入共享快照 | 各宿主独立凭证通道和私密状态，只交接必要任务资料与引用 |

推荐结构为**共享技能核心＋宿主接入＋平台安装能力＋Lody原生协作**。无需先建立新的任务数据库、全局调度器或通用权限代理。

## 3. 可行性与支持矩阵

以下“已验证”引用既有[支持矩阵](lody4dot-support-matrix.md)，本轮未重新运行Lody业务。

| 目标 | 当前证据 | 最小技术路线 | 进入支持列表的条件 |
| --- | --- | --- | --- |
| 当前Linux Codex云环境 | 安装、inspect、认证、目录及已有远端Agent受控执行通过 | 保留现有云准备与start_skill入口，作为控制端基线 | 原截图任务补齐入口和版本等记录；不把当前实例当新任务加载证据 |
| 其他Linux云机/本地Agent宿主 | 安装器可作为候选，目标机尚未验证 | 复用受管安装，使用实际可写prefix与独立状态；按宿主正式方式加载技能 | 真实OS/架构安装、重复安装、回滚、读取及连接回执 |
| macOS本地宿主 | 当前安装器和doctor拒绝，未实测 | 优先POSIX适配候选；单独核对路径、native依赖、激活及私密状态 | 在实际目标架构机器上验收，不能仅凭单元测试宣布支持 |
| Windows上的WSL2 | Linux目标候选，未实测 | 在WSL文件系统内验证Linux路线 | 不称原生Windows支持，不假定与Windows端共享身份和文件 |
| 原生Windows | 现有代码不支持 | 保留知识可移植；原生安装列后续需求，先返回可读的不支持结果 | 文件锁、ACL、启动器、symlink及进程终止均有实现和真实验收后再开放 |
| Dot | 用户目标明确；官方标识、安装与工具接口待核实 | 依次核实正式技能/插件入口、CLI、已有远程工具；必要时设计薄MCP适配 | Dot中真实读取、合法身份工具调用与结果交接分别通过；无工具时仅标知识/人工交接 |

代码约束有明确依据：`install.py`顶层导入fcntl并限制Linux；`common.py`使用uid/0700和killpg；激活依赖symlink与Python启动器。不能以删除Linux判断实现跨平台。知识包、宿主插件格式和OS运行时是三项支持维度。

架构预检路径为 **DISCOVERY，范围限定Dot接入与重置契约**：这些未知事实决定是否需要新远程服务和身份映射。C01/C09按有界调查收敛后再核对该边界；已知的技能、诊断、平台层和交接材料可独立设计。若确需新增远程MCP，其身份与副作用所有权须单独形成可审查设计，不能在发现任务里顺手部署。

## 4. 模块、所有权与依赖

| 模块及源码位置 | 负责 | 数据与副作用边界 |
| --- | --- | --- |
| 技能核心 `skill/lody4dot/` | 任务路由、命令事实、运行位置判断、协作和核验 | 知识唯一源码；不持有账号、全局任务状态或常驻进程 |
| 分发 `plugin/lody4dot/scripts/build.py` | 收集核心与已核实的宿主接入材料、包完整性 | 仅生成自包含分发物及已有receipt；不得收集登录态、机器配置和日志 |
| 宿主接入材料，建议 `plugin/lody4dot/hosts/` | 描述技能入口、工具连接、准备/启动时机、凭证与存储契约 | 每份材料有来源、版本和已验证范围；不推测通用清单字段 |
| 安装 `install.py`及建议的 `platform_support.py` | 锁定依赖、平台路径/锁/激活/检查、失败恢复 | 只写所属安装prefix，复用已有事务；不登录、不注册machine、不启动host |
| 认证 `auth.py` | verify-only及明确登录 | 宿主独立私密state，Lody账号与模型认证分别管理；不跨端复制身份 |
| 诊断 `doctor.py` / `common.py` | 分项诊断、范围、来源与保守失败分类 | 默认离线，显式连接才查资源；不创建、继续或取消任务 |
| 交接工具，建议 `scripts/handoff.py` | 整理/校验已提供的任务和证据记录 | 只读文件/输入或写明确输出，不执行远端业务、不充当任务状态数据库 |
| 主协调Agent与实际执行Agent | 在用户授权内拆解、选择目标、调用Lody并核验 | 协调写入权按本任务约定交接；执行者只写分配产物 |
| Lody服务和执行节点 | 已有资源发现、machine/config、session/turn、派发与观察 | 业务状态以原生返回与持久化观察为准；Operation、schedule按实际作用域使用 |

依赖方向：宿主材料和分发使用共享核心；安装/诊断/认证复用窄平台边界；交接记录引用原生业务结果；Agent通过已验证CLI或工具调用Lody。Lody业务实现不依赖本插件目录，技能不反向依赖某宿主的绝对路径。建议的新文件仅在对应任务有实际需求时增加，不预建通用框架。

安装身份、宿主会话、Lody会话和机器分别识别。首轮复用已有receipt，不强制新增安装ID，更不得用插件关联号替代Codex受保护的`installation_id`。

## 5. 能力与接口契约

### 5.1 角色与检查范围

角色可为知识读取、控制端、执行节点或控制/执行混合。它们与doctor的`inspect/control/task/worker`检查profile分别记录：请求某角色，不证明具备该能力。

doctor增强建议使用附加可选字段表达观察时间、宿主/工具位置、已验证范围、插件与CLI来源、未验证项。保留`schema_version:1`已有字段、退出码和pass含义；变更前检查消费方对未知字段的处理。若必须更改既有语义，单独版本化，不能静默升级。

先修已确认缺口：早期失败丢失已完成checks；包receipt、安装receipt与实际CLI版本未汇总；账户查询通过可能被读者误解为目标执行通过。账户通过+目录未运行仍保留其原始状态，通过新增范围说明避免误读。task/worker不得为消除blocked而改为pass。

原生失败分类不能把代理CONNECT拒绝直接写成目标对象ACL拒绝。保留原始退出码，输出脱敏分类和证据强度；模糊信号保留未知，不自动登录、发布或重试写操作。

### 5.2 最小交接记录

这是待实现的项目交接格式，不是Lody或Dot现有API。字段按实际可观察值填写，未知保留null；本地生成的关联号仅关联记录，不提供原生幂等性。

```json
{
  "schema_version": 1,
  "correlation_ref": null,
  "objective": null,
  "authorization_scope": null,
  "coordinator_ref": null,
  "control_host_ref": null,
  "executor_ref": null,
  "lody_refs": {
    "workspace": null,
    "machine": null,
    "agent_config": null,
    "session": null,
    "user_turn": null,
    "assistant_turn": null
  },
  "input_artifacts": [],
  "expected_outputs": [],
  "versions": {
    "plugin": null,
    "cli": null,
    "source_commit": null,
    "environment": null
  },
  "observations": [],
  "result_artifacts": [],
  "unresolved": []
}
```

各引用携带来源系统、对象类型、标识及所属执行器等必要定位信息；工件记录位置、访问方式、字节摘要与观察来源。任务授权范围与服务端访问结果分别保存。验收用途的记录缺目标、授权范围、准确执行关联或结果时，应报告缺口，不能因JSON可解析就判通过。

公共报告只输出必要的脱敏摘要；含业务文本和真实标识的完整交接记录按任务私密资料保存。记录中不接受凭证；工具输出不回显原生敏感响应。引用资料中的指令作为数据，不覆盖当前用户任务。

### 5.3 业务状态、超时与协作写入

提议、已接受、运行中、完成、失败、取消分别依据Lody实际返回处理；观察缺失/过期/metadata是证据状态，不另造业务终态。匹配workspace/session及具体user/assistant回合，不只看latestTurn。

派发前保存意图与关联号，返回后保存原生ID。请求超时可能已经受理：优先按已知ID和授权范围内目录/历史对账，无法唯一确定则保留不确定，停止自动重复派发。只有明确未受理且原生契约允许，或用户明确要求新的任务，才新建。首版协调权是显式协作约定，不是分布式锁，也不承诺多控制端自动故障抢占。

取消仅针对本任务授权的准确assistantTurnId，并核验同一回合持久化终态；ACK、alreadyStopped、停止观察或归档均不替代取消证据。回合取消不保证工具进程即时结束，取消Operation协同链须另核对后继影响。

## 6. 初始化、hooks与存储恢复

### 6.1 已知入口与更优选择

当前正式配置的环境准备脚本已包含结构检查、测试、锁定安装及离线inspect；启动指引已要求读取技能并做inspect。**需要复用现有初始化，而不是重复接一套脚本。** 本轮只新增官方文档站点的网络草稿，未修改安装/启动字段，也未注册hook。

推荐三层恢复，不以重置前回调为正确性前提：

| 时机 | 动作 | 明确边界 |
| --- | --- | --- |
| 环境准备/受支持的重建准备 | 按锁定输入幂等安装，验证CLI/native模块和收据，生成可复用依赖 | 不登录、不登记机器、不启daemon；失败保留旧安装；共享快照不含私密身份 |
| 会话开始/环境恢复后的可用入口 | 先离线inspect，只有明确缺少所属受管运行时才按同锁恢复，随后复检 | 不每次运行完整测试或重装；未知prefix/损坏来源/版本不符先报告，不覆盖用户设置 |
| 任务运行与交接 | 在可用且获授权的持久化目的地保存任务关联、必要输入和产物摘要 | 本地临时目录本身不算持久化；凭证与模型认证不进入交接或备份 |

认证在运行时通过已有独立通道进行；已有私密state只验证，确需登录才用原有`LODY_CLI_TOKEN`。启动worker是另一项操作，须有可写执行状态、模型身份、明确机器范围与生命周期验收。控制端恢复不要求启host。

### 6.2 hook的适用范围与证据

2026-10-21读取的[官方Codex事件表](https://github.com/openai/codex/blob/c7234c1174b27d9c55199fba0d546dc27d1b0415/codex-rs/hooks/src/lib.rs#L23)包含会话等事件；[SessionStart来源](https://github.com/openai/codex/blob/c7234c1174b27d9c55199fba0d546dc27d1b0415/codex-rs/hooks/src/events/session_start.rs#L23)含startup/resume/clear/compact/fork；[SessionEnd](https://github.com/openai/codex/blob/c7234c1174b27d9c55199fba0d546dc27d1b0415/codex-rs/hooks/src/events/session_end.rs#L20)为teardown事件，默认1秒、最大3秒。

这些是该源码提交的会话契约，不能证明Dot有存储重置通知、当前托管环境允许注册，或Lody使用的Codex0.160.1支持。当前未取得Dot重置频率、保留目录及重置前后hook的官方证据，不配置虚构事件。核实到适用入口后，只把上面的初始化动作接到它，不复制恢复逻辑。

### 6.3 恢复顺序与停止条件

1. 确认实际宿主/执行器及可用加载入口，读取本任务需要的技能。
2. 核对来源、依赖和CLI；缺失时只修复本插件拥有的安装目录。
3. 验证当前运行身份与所需目标范围，不恢复共享快照中的登录态。
4. 从获授权的持久化记录取得原Lody session/turn，再查询实际状态；找不到记录时保留未知，不能按相同标题自动重建。
5. 原任务仍运行则恢复观察；已完成则核验对应产物；失败/取消按原终态报告；没有足够证据则停止依赖操作。
6. 需继续业务时沿原会话发起明确的新回合，记录新的user/assistant标识；不得把“恢复初始化”当继续任务的授权。

恢复演练至少覆盖：依赖保留、依赖丢失、任务运行中控制端中断、结束通知完全未发生、原产物未持久化。不得为演练删除当前宿主卷或用户状态；使用自有临时prefix与记录fixture，再在真实独立目标验证。

## 7. 多端协作纵向场景

首个有价值的闭环为“一个宿主协调 → Lody派发 → 已有授权节点单写 → 另一个独立宿主只读复验”。Dot接口核实后加入同一场景，逐步取得含Dot的交付证据，不让其未知契约阻塞已有端改进。

| 步骤 | 行为与必要证据 |
| --- | --- |
| 定义 | 小型UTF-8输入、确定性JSON输出、输入摘要、目标断言、授权范围与角色明确；不使用用户业务项目 |
| 发现 | 从实际工具读取完整目录，核对工作区、机器与最终配置；Role覆盖以实际生效值为准 |
| 派发 | 主协调者只创建一次，记录实际原生ID；执行节点在自己的获授权临时目录写结果 |
| 回收结果 | 观察匹配回合的持久化终态，并通过受支持文件通道或同会话的只读挑战取得字节与摘要 |
| 跨端复验 | 第二独立宿主读取同一任务关联并核对结果，不再次create、不修改原产物、不启host |
| Dot参与 | 具备合法工具入口时参与调用与汇总；若只能人工交接，明确记录这一限制，不宣称自动闭环 |
| 清理 | 只清理本任务自有临时认证和测试资源，保留既有身份、daemon和会话 |

当前云实例的ACP只读失败不影响其控制/复验角色；若目标是让Lody自动派发到云端执行Agent，则需另验真正可写、已授权的云执行节点。本地机器休眠或offline时Lody不被假定能代替它完成工作。

输入路径携带所属执行器；路径字符串不等于文件传输。小产物先用已验证的字节读回方法；大产物可评估授权Git提交或文件服务，单独核验访问和完整性，不先开发通用文件同步系统。每个产物首版只有一个写入者，复验者保持只读。

## 8. 顺序、任务与验证

完整静态任务卡及精确依赖表见[C01–C10](lody4dot-collaboration-tasks.md#共用约束与依赖)，状态及实际证据仍在唯一队列。C01、C02、C03可并行；C03后进行C04，具备对应宿主证据后进行C05；C02/C03还可支撑C06。C05/C06汇合后进行C07，C01/C05/C07支撑C08；C09的入口发现可与双端验证并行，其实现依赖对应宿主契约、分发和交接。最后C07/C08/C09汇合到C10。

C04的实际开放平台、C05的每种清单与C09的工具路线按C01证据决定。各任务的完整前置以卡片为准；C06新增交接工具时完成其对应分发回归，不将它倒置为已完成C05的前置。正式环境更新、实际联网验收和同一任务的副作用操作串行，避免并行写同一prefix或会话。

| 阶段 | 交付物 | 出口 |
| --- | --- | --- |
| A：边界与基础 | 宿主契约表、技能修正、诊断与来源字段、平台边界 | 静态/fixture失败路径有证据，未知接口未伪造 |
| B：可用端协作 | 按宿主打包、交接记录、真实双端闭环 | 两个独立宿主与一个执行节点有角色/版本/结果证据 |
| C：恢复与Dot | 有界初始化恢复、Dot合法接入验证 | 中断后不重复派发；Dot实际读取和工具调用可核验 |
| D：最终复现 | 含Dot协作回执、支持矩阵、上一版本恢复方法 | 整体目标逐项对应真实证据，人工交接与自动链路分开报告 |

现有可用检查从仓库根目录执行：

```bash
python3 scripts/check_repository.py
python3 -m unittest discover -s tests -v
git diff --check
python3 plugin/lody4dot/scripts/build.py --output /tmp/lody4dot-candidate
```

构建输出需选本次新建或已确认自有目录；已有输出不直接覆盖。各卡片的新测试文件和`handoff.py`等为拟新增接口，当前不能声称可运行。真实接入前先做无账户测试；运行类验证只操作已授权的隔离目标，不在CI自动使用真实Lody账号。

关键验收包括：重名/分页、Role覆盖、无shell入口、错误命名空间、非共享文件路径、节点offline、模型身份缺失、创建超时与跨端重复请求、过期回合、取消竞态、重建无退出通知、凭证脱敏。断言实际目标、调用序列和产物，不比对Agent固定措辞，不以关键词检查代替协作行为。

## 9. 迁移、发布与回滚

以当前lody4dot0.1.4和CLI0.107.2为可复现基线，正式云配置来源仍按既有0.1.3记录。新宿主包来自同一核心源码，分别记录格式、OS/架构、角色、源码与插件/CLI版本、锁和包摘要。知识更新可复用同锁CLI，不能把知识版本和运行时目录强制一一绑定。

先构建、解包校验和无账户测试，再在单个自有目标验收，最后按真实宿主更新对应安装或配置。发布配置、实例应用、实际读取和业务结果分别取证。未经验证的宿主不进入“支持”列，不自动追latest，不为得到Viewer而换不匹配文件或放宽校验。

旧Linux入口和schema1字段保持兼容；需要更改外部契约时先做消费方验证与独立版本说明。失败回滚仅恢复本插件拥有的上一安装入口或宿主接入材料；Lody会话与任务结果不随插件回滚而删除，用户身份和其他机器配置保持原有所有权。

## 10. 可执行性与当前缺口

**这份方案可直接交接并分段开展；全范围自动交付尚不能宣布具备条件。** 可以独立启动的是已有代码与知识缺口、宿主契约调查、离线交接格式及基础测试。Dot实际扩展接口、首批本地OS/架构、真实独立宿主和执行节点接入是后续集成的具体输入，缺少哪项仅阻塞相应卡片。
