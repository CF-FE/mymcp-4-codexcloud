# 迭代周期与已知行为

迭代是日期区间，不是把操作重复执行多次。只有任务需要迭代字段时读取本页。

## 已知证据边界

2026-10-27两端报告发现：`create_iteration_field` 要求顶层 `start_date`；仅给 `iterations[].start_date` 不够。Lody端省略 `iterations` 的创建返回及后续读取均为空周期列表，与其当时工具描述的自动生成3期不一致；显式列表的创建、赋值、批量切换及清空已验。另一端的显式创建成功不关闭这个异常。

[上游固定实现](https://github.com/github/github-mcp-server/blob/b98d115bbb080e9555466a96656ec4df605aea21/pkg/github/projects.go#L2669-L2811)先创建字段，再解析部分日期／周期参数并第二次更新配置；省略列表时发送空数组。这支持输入需在写入前校验、报错需先查已有副作用的处理。远端部署 SHA 未知，此源码不是其版本证明；失败遗留字段的负向场景尚未真实测试。

## 显式计划再写入

复用用户或项目已经约定的开始日期、每期天数、期数和标题规则。没有必要参数时先补所需信息或给出明确待接受方案；不把历史测试的3期、7天和日期当业务默认，也不为了读进度创建迭代字段。

1. 写前验证有效日历日期、正整数天数／期数、非空标题，并核各周期与已约定计划一致。日期按日历日计算，不用秒数跨时区推算。
2. `create_iteration_field` 同时传顶层 `start_date`、`iteration_duration` 和非空 `iterations`。字段名称、owner／owner_type／project_number 来自实际任务。
3. 保存返回字段 ID；若返回的是 node ID，先沿原项目字段列表定位数值 ID，不强制转型。再用 `get_project_field` 核实际期数、每期标题、开始日期、天数及周期 ID。调用成功但缺期仍是不符合预期，不能宣称服务端默认分支已修复。
4. 赋值使用回读的周期 ID，字段名与字段 ID 的选择以当前方法支持为准。`null` 清空迭代值有历史实测；不能推广到所有字段类型。
5. 创建超时或配置失败，先按原目标与唯一字段名／已知 ID 查询。已创建空字段是部分结果，不再创建同名字段补救；当前工具未提供已有迭代字段的配置更新或字段删除方法，按授权决定后续处理，不编造修复调用。

已有授权且目标未变时不逐步重复请示。确需重验上游默认分支时单独定义预期、测试对象和保留策略，不在业务项目自动做回归。

## 可选离线生成器

等长且连续的周期可使用随包的[日期规划脚本](../scripts/plan_iterations.py)，只依赖Python 3.10+标准库，不读凭证、不联网、不调用MCP、不写文件。普通查询／更新无需Python。

从技能目录运行，以下仅生成示例计划，尚不是写入授权：

```bash
python3 scripts/plan_iterations.py --start 2028-02-26 --days 7 --count 3 --title-prefix Sprint
```

输出 `start_date`、`iteration_duration`、`iterations`，可与已核准的实际目标参数合并。所有参数必须显式给出；有间隔或不等长的业务计划直接构造并检查其准确日期，不用等长脚本覆盖它。没有Python时可用当前宿主已有的日历计算能力完成同样的输入校验和计划，不安装运行时作为普通操作的前提。
